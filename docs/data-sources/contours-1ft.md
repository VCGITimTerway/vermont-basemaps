# 1' Contours (QL2 Lidar-Derived)

## What is this data?

Statewide 1-foot contour lines derived from lidar — finer interval than
the "major"/labeled contours shown at small scale, used for the
zoom-dependent contour basemap layer tested in
[`../dem-color-ramps/11class-monochrome-canvas/`](../dem-color-ramps/11class-monochrome-canvas/README.md)
(e.g. the 250 ft-interval contours visible in that variant's screenshots
are a generalized/filtered subset of this source at those zoom levels).

**Important: this is a different, older, and lower-resolution lidar source
than the [Bare Earth DEM](dem-bare-earth.md)** — see Derivation below. Any
visible misalignment between contour lines and the DEM-based hypsometric
tint or hillshade in this repo's basemaps is expected, not a bug, until/
unless the contours are regenerated from the 2023 QL1 data.

  (generalized version; the pre-generalization source is
  `ElevationContours_CN1T`, also published)

## Derivation

- **Input sources: five separate, older QL2 lidar collections, not the
  2023 QL1 acquisition used for the DEM:**

  | Collection | Area | Dates | Datum |
  |---|---|---|---|
  | Rutland/Grand Isle 2013 | Rutland & Grand Isle Counties | 2013-11-04 to 2014-10-24 | NAD83 (plain, not 2011) |
  | Eastern VT 2014 | "Lot 7", Eastern VT | 2014-10-24 to 2015-04-28 | NAD83(2011) |
  | Windham County 2015 | Windham County | 2015-11-03 to 2015-11-11 | NAD83 (NSRS2007) |
  | Mid-CT River Basin 2016 | CT River Basin | 2016-11-01 to 2016-11-19 | NAD83(2011) |
  | Western VT 2017 | Addison, Bennington & Franklin Counties | 2017-11-08 to 2017-11-21 | NAD83(2011) |

  All QL2 (0.7 m nominal pulse spacing) — roughly half the point density
  of the DEM's QL1 (0.35 m) source. Vendor: Quantum Spatial. **Three
  different horizontal datum realizations across the five collections**
  (plain NAD83, NAD83(NSRS2007), NAD83(2011)) — the published metadata
  explicitly defers to each vendor's own report for exact coordinate
  reference details rather than asserting one unified datum.
- **Methodology:**
  1. Contours generated by each vendor from that collection's classified
     lidar (process predates VCGI's involvement in detail).
  2. Imported/reprojected/renamed into one statewide schema by VCGI across
     2016–2018 as collections arrived.
  3. Generalized (simplified) using a 0.1 m tolerance in 2022 to produce
     this (`CN1TGEN`) version from the full-detail `CN1T` version.
- **Known defect (stated in the metadata itself):** *"The square meter
  area threshold settings selected by the vendor resulted in missing
  contour lines from on top of summit features throughout the state."*
  This is a documented, acknowledged gap, not a rumor — worth checking
  specifically at mountain summits in any basemap using this layer.
- **Attribute schema (`TYPE` field, from the published metadata):**
  - `'Contour Line, Index Major'` — major 20 ft intervals (elevations
    ending in 00, 20, 40, 60, 80)
  - `'Contour Line, Index Minor'` — minor index 10 ft intervals
    (elevations ending in 10, 30, 50, 70, 90)
  - `'Contour Line, Intermediate Even'` — even single-foot intervals
  - `'Contour Line, Intermediate Odd'` — odd single-foot intervals

  This is exactly the field/value set needed to build the zoom-dependent
  styling (index vs. intermediate contour weight/color) discussed in
  [`../dem-color-ramps/11class-monochrome-canvas/README.md`](../dem-color-ramps/11class-monochrome-canvas/README.md#companion-layers).

## Use cases & limitations

- **Intended use cases:** Basemap contour layer, zoom-dependent interval
  (e.g. coarser intervals at small scale, full 1 ft detail at large scale).
- **Known limitations / caveats:**
  - **Vintage/resolution mismatch with the DEM** — this is 2013–2017 QL2
    data; the DEM/hillshade this repo's color ramps are built on is 2023
    QL1. Terrain that's changed since 2013–2017 (quarries, development,
    streambank erosion) won't match between the two layers.
  - **Datum mismatch** — the published horizontal datum here is plain
    "North American Datum of 1983" in the metadata's spatial reference
    section (not 2011), while the DEM is NAD83(2011). Likely a small
    practical difference at basemap scales, but not zero, and compounds
    with the three-way datum split across source collections above.
  - **Missing summit contours** (documented defect, see above).
  - Vertical accuracy standard here (FVA 18.13 cm at 95% confidence,
    computed on raw point-cloud swaths) is a looser/different accuracy
    framework than the DEM's (NVA/VVA with 348 independent checkpoints) —
    not directly comparable.
  - Vertical units are **US feet** here (confirmed in the metadata's
    spatial reference section — `Altitude_Distance_Units: U.S. feet`),
    unlike the DEM/hillshade which are in meters.
- **Appropriate scale / zoom range:** Zoom-dependent by design, and this
  is enforced server-side, not just by style convention — confirmed by
  decoding actual tiles directly from the VectorTileServer: 1000ft
  interval only exists in tiles at z7–10, 500ft first appears at z11,
  250ft at z12, 100ft at z13, and so on. The finer intervals are
  genuinely absent from the tile data below their zoom, not merely
  filtered out by a style's `minzoom`/`maxzoom` — a consuming style
  cannot show finer detail earlier than this without the service itself
  being republished with different zoom-tier assignments. This exactly
  matches Esri's own factory-default style's zoom breaks for this
  service, confirmed when investigating whether the
  [dark-olive style](../contour-styles/dark-olive/README.md#to-revisit)'s
  sparse Champlain Valley contours at low zoom could be improved —
  they couldn't, via styling alone.

## Current source

**Not a hosted feature layer** — unlike most other VSDI vector layers,
published only via ArcGIS Server/AGOL tile services, with no feature
service identified yet:

- **Service:** [ArcGIS Server MapServer, cached](https://maps.vcgi.vermont.gov/arcgis/rest/services/EGC_services/MAP_VCGI_LIDARCONTOURS_WM_CACHE_v1/MapServer)
- **Service (vector tiles):** [Esri Vector Tile Service](https://tiles.arcgis.com/tiles/BkFxaEFNwHqX3tAw/arcgis/rest/services/VECTOR_VCGI_CN1TGEN_WM_v1/VectorTileServer)
- **Format:** Cached map tiles (first service) + pre-built vector tiles
  (second service) — both are already-tiled outputs, not a queryable
  feature service
- **Projection (EPSG):** EPSG:3857 (Web Mercator), confirmed for both
  services
- **Geometry type:** Line

## Path to PMTiles / TiTiler output

- **Target format:** PMTiles (vector), for open-source/MapLibre
  consumption
- **Pipeline steps:**
  1. **Blocked on finding a source-of-truth export.** Neither existing
     service is a queryable feature service — the standard AGOL hosted
     feature layer → FlatGeobuf/GeoJSON → tippecanoe path assumed
     elsewhere in this repo doesn't have an obvious starting point here.
     Need to identify whether an underlying feature class/feature service
     exists (e.g. in ArcGIS Server's `EGC_services`) that the Vector Tile
     Service was itself generated from, and use that as the PMTiles
     source instead of trying to extract geometry from the tile services.
  2. Once a source export exists: standard tippecanoe → PMTiles pipeline
     (see [`../architecture/foundational-layers.md`](../architecture/foundational-layers.md#vector--pmtiles--parallel-esri-vector-tiles)).
- **Known gaps / blockers:**
  - This is the clearest existing case of the "two independent pipelines"
    problem in the architecture doc (gap #1) — the cached MapServer and
    the Vector Tile Service are not confirmed to be generated from a
    shared export.
  - No PMTiles equivalent exists yet.
  - Styling is currently authored directly in Esri's Vector Tile Style
    Editor against the existing Vector Tile Service (see the contour
    color work in
    [`../dem-color-ramps/11class-monochrome-canvas/`](../dem-color-ramps/11class-monochrome-canvas/README.md))
    — once a MapLibre `style.json` exists for the PMTiles version, the two
    styles will need to be kept in sync by hand (architecture doc gap #3).
